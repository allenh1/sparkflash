## 3. Criterion 1 (device-forward-chain.md section 4.3) - OPEN and measured failing

The criterion is one `--phase full --prompt 130 --decode 8` run reproducing the tokens
`491, 367, 201, 80, 3302, 201, 54, 201, 4341` at positions 129..137 with the position-129 logits at
the 2e-2 bar. It is **not met**:

- The first complete 130+8 run (b68) gives the hard numbers: at position 129,
  `128528 of 129280 compared logits` are outside the 0.02 bar (`max |difference| 15.009581`,
  argmax 8060), and the nine device tokens are **8060, 8060, 1168, 50673, 303, 531, 6525, 5719,
  14171** against the fixture's **491, 367, 201, 80, 3302, 201, 54, 201, 4341** - **0 of 9**. The
  head A/B twin shows the head input has drifted by 0.608 max, and the hybrid logits are ~20%
  flatter (15.73/15.43/14.56 against 19.85/21.25/16.97 at positions 0/1/2).
- Every separable stage passes its own bar: alignment and the pre-attention hidden are exact
  (4/5,120 bf16 mismatches, max_abs 2.83e-7), the format-2 body matches on identical staged operands
  (35/18/13 of 40 layers zero-mismatch, max_abs <= 7.8e-3), `wq_b` **exactly** reproduces `mxfp8_ref`
  (0/32,768, max_abs 0.0), and the device head reduce equals the host four-shard assembly at every
  position (`block_max_equal=true`).

**Root-cause chain (measured, not hypothesised).** The device attention path quantises its
activations to MXFP8 (32-element blocks, power-of-two ceil scales) while the fixture reference
computes f32 over dequantised weights. That costs ~3.1e-2 at layer-0 post-attention and ~2.0e-2 at
the layer-0 host FFN output; the drift propagates into the router input, where **the first real
expert-set flip is layer 3** (`scores_max_abs=1.472694e-2` there, growing to 1.311 at layer 39;
36 of 40 layers have a different expert set at position 0), and layer 0 keeps the reference set only
until the 1.65e-2 score drift reaches the first tie. The **BF16 control is decisive**: quantising the
f32 reference's own router input to BF16 never changes its expert set and never matches the device
set, so this is **attention-path drift flipping router selection at layer 3**, not BF16 staging and
not a router-kernel defect (the router kernel matches its own BF16 host to 5.96e-8).

Criterion 1 therefore fails the *f32-simulation* comparison; exact token parity against the f32 reference is not attainable with native MXFP8 activations. D37 records that; the user decided it on 2026-10-19 (D39): the native arithmetic stays and the token criterion is replaced by a numeric, tolerance-based comparison.

## 4. The decision that is waiting (superseded 2026-10-19 by D39: native arithmetic stays, numeric criterion)

Two families, not mutually exclusive:

1. **Precision-first activation path** (keeps the criterion as written). Options, cheapest first:
   BF16 activations with dequantised weights for the five attention projections and the router
   (small weight sets, no memory blow-up; MoE activations stay quantised), or a writer's guess at a native FP8 activation rule (per-1x128 block, exact scale rather than power-of-two ceil). **Correction (D39):** that parenthetical is not this checkpoint's rule - the released forward quantises activations in 32-element blocks with power-of-two ceil scales (model.py:27-30, 182-205; kernel.py:98-124; D23), and that is exactly what the device already does. This family is rejected.
2. **Criterion redefinition** (keeps the current arithmetic). Compare against a same-arithmetic
   reference, or accept a tolerance/perplexity-style bar, and record what vLLM-quality serving
   actually requires. D38 means a vLLM comparison needs a server holding our snapshot, not the
   heretic variant currently deployed.

Recommendation from the evidence: do (1) for the attention projections and router at minimum, because
a router set flip at layer 3 is a large discrete error and the 0.608 head-input drift is far beyond
what an FP8-native serving stack would show; then keep (2) as the acceptance language for the MoE
activation stage that cannot be made f32 at this memory budget.
